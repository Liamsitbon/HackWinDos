# USB1 discovery window and non-destructive state capture

EXP037/IMG_6313 did not produce USB boot after the PHY-role-only change. Its early SIG readback was missed; Shell shows firmware, RAM disk and internal NVMe only. Do not infer the host role readback or root-port connection from that screen.

Fresh macOS evidence: SanDisk VID 0781/PID 5595 is under USB1, linked at 480Mb/s, bcdUSB 0x0210, interface class 8/subclass 6/protocol 0x50 (SCSI Bulk-Only). Thus USB2-only firmware is not inherently excluded by this stick. WININSTALL contains valid ARM64 fallback, BCD, boot.wim and boot.sdi; boot.wim integrity verification passed. M2BOOT has fallback/BCD but lacks boot.wim/boot.sdi; this is a later media-selection concern, not an explanation for zero physical USB paths. No media change authorized/performed by this inspection.

Sources inspected in required order: current macOS ADT/IORegistry/descriptors and IMG6313; Asahi T8112 DTS, drivers/phy/apple/atc.c and drivers/usb/dwc3/dwc3-apple.c; local m1n1 usb.c, runtime guest mappings and profile/PHY initialization; Mu Apple USB/DART owners, generated J413 ACPI, DXE CoreConnectSingleController, Xhci.c/XhciReg.h, UsbHub.c/UsbBus.c, current selection and phase log; official Microsoft USB host architecture documentation. Prior assisted J313 and standalone J413 contracts are EXP028–037 and documentation/DEBUGGING.md. References remain the primary Asahi sources and https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-3-0-driver-stack-architecture . No external implementation code copied.

Ownership remains m1n1 for platform PHY/power and mappings; Mu for DART/xHCI/UsbBus/media/BDS; Windows inbox USBXHCI after ExitBootServices. No reset, clock, interrupt, DMA or Windows-driver change is justified without a root-port/PHY snapshot. CoreConnectSingleController already retries drivers on the same handle; UsbRootHubInit waits for six 100ms polls. A second global ConnectAll or guessed register setting is not justified.

Confirmed selection defect: discovery permanently latches its first filesystem snapshot, including absence. Existing asynchronous USB timers may publish a later filesystem, but it can never be considered by that selector. Correct that layer with a bounded application-level event-driven retry only when the exact loader is absent. Retry policy is 10 seconds at 200ms timer intervals, not a claimed hardware timing requirement. No busy Stall or TPL_CALLBACK image services. Once a candidate exists, retain normal BDS launch and one-pass candidate iteration. Do not search arbitrary EFI files.

Diagnostic addition: on final not-found, print an updated inventory, USB bus binding status, raw xHCI CAP/command/status/PORTSC through bounded PCI I/O reads, and USB1 PHY USBCTL/CTL/SIG/MISCTUNE through validated live ADT resources. Do not call GetRootHubPortStatus for diagnostics: the pinned implementation acknowledges change bits and may configure slots. Use read operations only. Keep a timed 30-second failure-screen window, with callbacks enabled, to let the operator photograph the late snapshot before the normal Shell mapping output replaces it. This diagnostic delay is explicitly measured and not a hardware initialization change.

Falsifiable checkpoint: a filesystem appearing during the discovery deadline is selected; actual runtime snapshot distinguishes no UsbBus binding, no connected port, controller error, or descriptor/DMA failure. If all remain absent, the window correction is insufficient and the raw values govern the next experiment. Never call the build USB-compatible on host tests alone. Recovery: preserve EXP035 artifacts and actual installer backup before deployment; no reboot or install by this software work. Provide a freshly pinned installer with the candidate.
